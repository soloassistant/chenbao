## 一、权限模型（先看这个，决定你能读到什么）

| 表 | 普通用户 | 管理员 | 说明 |
|---|---|---|---|
| `orders` | 只读**自己**的 | 读**全部** | 客户端无 INSERT/UPDATE/DELETE（`REVOKE` + 触发器挡 `status='paid'`） |
| `paid_order_claims` | **无权限** | 只读全部 | 核销记录：哪笔订单发过权益 |
| `promo_codes` | **无权限** | 只读全部 | 只存 `sha256(大写码)`，明文永不入库 |
| `promo_redemptions` | **无权限** | 只读全部 | 谁兑了哪个码 |
| `admin_actions` | **无权限** | 只读全部 | 管理动作审计 |
| `app_admins` | **无权限** | **也无** | 只有 `is_app_admin()` 能读；加管理员需 service role |
| `user_kv` | 读写自己的 | 读全部 | 同步数据（24 个 SYNC_KEYS） |
| `llm_events` / `feedback` / `client_errors` | 只读自己 | 读全部 | 用量 / 反馈 / 崩溃 |

**「管理员」= `app_admins` 表里的 uid**（当前只有 `2108536518187421696`）。
判定函数：`rpc('is_app_admin')` → `true/false`，客户端可调，不泄露名单。

> ⚠️ 另有 6 个**遗留策略**仍硬编码同一个 uid（`client_errors_admin_select` /
> `feedback_admin_select` / `feedback_admin_update` / `llm_events_admin_select` /
> `orders_admin_select` / `user_kv_admin_select`）。它们**不在仓库里**、也不读 `app_admins`。
> 所以：**加第二个管理员时，这 6 处必须一起改**，否则新人看不到数据。
> 建议单独一笔 PR 改成 `public.is_app_admin()`。

## 二、订单一单一世界的状态口径

`orders` 关键列：

| 列 | 含义 | 注意 |
|---|---|---|
| `order_id` | 业务单号 | 主键语义；`h5p_*` = 支付网关单，`admin_grant_*` = 人工开通，`promo_*` = 兑换码 |
| `owner_id` | 归属账号 | 客户端**永远不传**，由服务端 `auth.uid()` 填充 |
| `plan_id` | `earlybird_monthly` / `monthly` / `yearly` / `promo` | |
| `channel` | `wechat_h5` / `admin_grant` / `promo` | **对账时按这个分** |
| `amount_cents` | **分** | 页面上除 100 显示元 |
| `months` | 30 天为一个月的月数 | 1 / 12 |
| `status` | `paid` 才算数 | 其余一律不计权益 |
| `refund_status` | `none` / `refunding` / `refunded` | `refunding`/`refunded` 都**不算有效权益** |
| `paid_at` | 支付时刻 | 权益回放按它排序；**没有 `paid_at` 的脏数据不参与** |

**「是否有效会员」的唯一算法**（前端 `entitlement.ts` 就是这个，后台请照抄，别自创）：

```
取 status='paid' 且 refund_status 不在 ('refunded','refunding') 且 paid_at 非空的订单
按 paid_at 升序
expiry = 第一笔的 paid_at 日期
对每笔：start = max(expiry, 该笔 paid_at 日期)；expiry = start + months×30 天
最终 expiry >= 今天 才算会员
```

> 逐笔累加而不是「最长那笔」——中断后再买的用户不吃亏也不白送。

## 三、四个管理接口（都已建好并验过）

### 1. 人工开通权益

```js
await rpc('admin_grant_membership', {
  p_order_id: 'h5p_1794392796858_c7cb990a',  // 支付平台的单号或后台生成的补单号
  p_owner_id: '<用户 uid>',
  p_plan_id: 'yearly',                        // earlybird_monthly | monthly | yearly
  p_amount_cents: 8800,                       // 分；核对流水后填真实金额
  p_reason: '用户反馈已付款未开通，核对微信流水号 xxx'  // 必填，≥4 字，进审计
})
// → { ok: true, already: false, months: 12 }
```

行为保证：
- **非管理员** → 抛「仅管理员可以人工开通」
- **同 `order_id` 重复调用** → `already: true`，**不会重复发权益**（与用户自助核销共用同一个唯一约束）
- 订单号已绑定别的账号 → 抛错（防串号）
- 套餐未知 / 原因太短 → 抛错
- 落 `orders` 时 `channel='admin_grant'`，对账时能与真实支付区分

### 2. 建码 / 更新码

```js
await rpc('admin_create_promo', {
  p_code: 'CHENBAO2026LAUNCH',   // 明文只在这次调用里出现，入库只存 sha256
  p_days: 30,                     // 1~366
  p_good_until: '2027-01-31'      // 不能早于今天
})
// → { ok: true, code_hash: '...', updated: false }
```

### 3. 停用 / 启用码

```js
await rpc('admin_set_promo_active', { p_code_hash: '<表里的 code_hash>', p_active: false })
```

### 4. 判断当前账号是不是管理员

```js
const isAdmin = await rpc('is_app_admin')   // true / false
```

## 四、对账要用的三个查询

### ① 付款了但没开通（最该天天看的一张表）

正常情况 `orders` 与 `paid_order_claims` 是**同一事务写**的，不一致就是异常：

```sql
-- 有订单、无核销记录（可能是人工直接插的 orders，或历史脏数据）
SELECT o.order_id, o.owner_id, o.channel, o.amount_cents, o.paid_at
  FROM public.orders o
  LEFT JOIN public.paid_order_claims c ON c.order_id = o.order_id
 WHERE o.status = 'paid' AND c.order_id IS NULL
 ORDER BY o.paid_at DESC;

-- 有核销记录、无订单（理论上不该出现；出现说明写了一半）
SELECT c.order_id, c.owner_id, c.plan_id, c.claimed_at
  FROM public.paid_order_claims c
  LEFT JOIN public.orders o ON o.order_id = c.order_id
 WHERE o.order_id IS NULL
 ORDER BY c.claimed_at DESC;
```

### ② 按天 / 渠道汇总（收入口径 = `amount_cents` 之和，排除已退款）

```sql
SELECT date_trunc('day', o.paid_at)::date AS day,
       o.channel,
       count(*)                            AS orders,
       sum(o.amount_cents) / 100.0         AS yuan
  FROM public.orders o
 WHERE o.status = 'paid'
   AND coalesce(o.refund_status, 'none') = 'none'
 GROUP BY 1, 2
 ORDER BY 1 DESC, 2;
```

### ③ 退款与异常

```sql
SELECT order_id, owner_id, channel, amount_cents, refund_status, paid_at
  FROM public.orders
 WHERE coalesce(refund_status, 'none') <> 'none'
 ORDER BY paid_at DESC;
```

## 六、两个必须知道的风险

1. **`banned_users` 权限失控**（本次未动，等你决定）：
   RLS 关闭 + `anon` 可读 + `authenticated` 有 `DELETE / UPDATE / TRUNCATE`。
   任何登录用户都能清空或篡改黑名单（被封的人可自己解封）。建议至少：
   ```sql
   REVOKE ALL ON TABLE public.banned_users FROM PUBLIC, anon, authenticated;
   -- 读名单只给管理员：GRANT SELECT + is_app_admin() 策略
   ```
   但它可能是平台侧在用，**改之前要确认**。

2. **管理员 uid 硬编码在 6 个遗留策略里**且不在仓库 —— 见第一节的警告。
