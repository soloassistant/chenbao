6. `执行后自检通过：函数权限已收紧、三表三项已收回、行数未变。`

出现 `执行后自检失败：…` 时按报错文本处置：

| 报错片段 | 含义 | 处置 |
|---|---|---|
| `public schema 缺少表 […]` | 表名/schema 不对，事务已整体回滚 | 核对表名后重跑 |
| `authenticated 没有 EXECUTE` | 函数权限没授上，已登录用户调不动 | 重看第 1/2 段是否真的执行 |
| `anon 仍可 EXECUTE` / `PUBLIC 仍可 EXECUTE（aclitem grantee=0）` | 授权来源不止一处（平台额外 GRANT / owner 隐式权限） | 用第 0/4 段打印的 `proacl` 定位，不要盲目重复 REVOKE |
| `… 行数变化 x → y（数据出事了）` | **提交后数据真被改了**，自检异常不会回滚 | 立刻停手，按备份恢复，禁止重跑 |

## 步骤 3：匿名验证（REST 直连，不经过 App）

在控制台之外（本机终端）执行，**不要把 service role key 贴进任何日志**：

```bash
curl -sS -i -X POST 'https://<应用数据库 REST 基址>/rpc/purge_my_h5_data' \
  -H 'apikey: <publishable key>' \
  -H 'Content-Type: application/json' \
  --data '{}'
```

期望结果：

- HTTP `401`（或 `403`），响应体里 `"code":"42501"` —— 收紧生效，匿名调不动删数据函数；
- HTTP `404` + `PGRST202` —— 函数没建成功（第 1 段被回滚），回步骤 1 重看输出；
- **HTTP `200` 且返回 `purged` 字段 —— 收紧没生效，匿名仍能清空数据。立即停止，不要发布。**

（`apikey` 用 publishable / anon key 即可；该请求**不带** `Authorization: Bearer <user JWT>`。）

## 已登录路径的说明

`authenticated` 仍保留 `EXECUTE`，所以正常登录用户在注销时调用该函数应当成功；
若线上出现 `42501` 且用户会话有效，说明 `authenticated` 授权被改坏，属真故障（客户端会以
`denied-authenticated` 走 `console.error` 留痕，不会被静默成灰度态）。
