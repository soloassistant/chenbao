# H5 支付权益闭环 —— 执行手册

> 代码侧已全部落地并过了门禁（`verify:h5pay` 34 条 + 9 条变异 + 端到端 11 条）。
> **但有一条必须人工执行**：数据库函数还没建，权益开不了。本文就是那一步。

---

## 一、现在缺什么（一句话）

支付网关确认「钱到了」之后，要由数据库函数 `redeem_paid_order` 验签并把订单写进
`orders` 表 —— 而 `orders` 写入被三重收紧（REVOKE + 触发器 + 唯一函数只认促销码），
所以必须新增这一个函数。**函数没部署 = 用户付了钱但开不了会员。**

代码行为对此是诚实的：函数不在时客户端会收到 `PGRST202`/权限错误，页面显示
「付款已到账，会员还没开通 + 订单号 + 请联系客服人工开通」，**不会谎报开通**。

## 三、执行 SQL（一次，可重复执行）

1. 打开 `.tools/sql/v9-h5-paid-orders.sql`，整份执行。
2. **紧接着插入验签密钥**（这一步不做，函数会一直拒绝）：

```sql
INSERT INTO public.app_secrets (name, value)
VALUES ('pay_gateway_hmac', encode(gen_random_bytes(32), 'hex'))
ON CONFLICT (name) DO NOTHING;

-- 取出它，等会儿配给网关（只在这一步看，别贴到任何文档/群里）
SELECT value FROM public.app_secrets WHERE name = 'pay_gateway_hmac';
```

3. 按文件末尾的自检 A~E 逐条跑，把结果贴进发布记录。要点：
   - A：`redeem_paid_order` 存在且 `prosecdef = t`
   - B：只有 `authenticated` 有 EXECUTE（**没有 PUBLIC / anon**）
   - C：`app_secrets` / `paid_order_claims` 对客户端三类角色**零授权**
   - D：密钥长度 64
   - E：乱造 sig 调用必须报「支付凭证验签失败」，且**不留下任何 orders / claims 行**

## 四、部署支付网关

```bash
# 必填
PORT=8080
XUNHUPAY_APPID=...              # 聚合支付商户 appid（虎皮椒/Xunhupay 一类）
XUNHUPAY_APPSECRET=...          # 聚合支付密钥（只在这里，绝不进前端）
PAY_GATEWAY_HMAC_SECRET=...     # 与第三步 app_secrets 里那个串**必须逐字符相同**
PAY_NOTIFY_URL=https://<网关域名>/notify
PAY_RETURN_URL=https://<前端域名>/#/pages/membership/index
PAY_PUBLIC_BASE=https://<网关域名>
PAY_LEDGER_FILE=/var/lib/paygw/orders.json   # 落盘账本，强烈建议配置
PAY_CORS_ORIGIN=https://<前端域名>           # 别留 *

# 启动
node server/pay-gateway/index.mjs
```

启动后先自检：

```bash
curl https://<网关域名>/health
# 期望：{"ok":true,"configured":true,"claimReady":true,"provider":"xunhupay"}
# configured=false → 商户参数没配；claimReady=false → HMAC 密钥没配/太短
```

前端构建时注入网关地址（不注入 = 支付入口不出现，页面走促销码兑换）：

```bash
H5_PAY_GATEWAY=https://<网关域名> yarn build:h5
```

### 两个必须知道的部署约束

1. **账本要落盘**（`PAY_LEDGER_FILE`）。不落盘的话，进程重启后「这笔订单买了什么套餐」
   就丢了 —— 用户付完钱回来签不出凭证，等于钱收了开不了会员。
2. **单实例假设**。账本是本地文件，多实例部署时 A 实例下的单 B 实例查不到。
   要水平扩展需换共享存储（Redis / PG），别直接堆副本。

## 五、上线前怎么验（真钱之前先验这些）

1. **未配置路径**：不填 `XUNHUPAY_*` 启动 → `/order/create` 必须 503 `unconfigured`，
   前端「立即订阅」必须显示「在线支付还没开通」并保留促销码入口。
2. **负路径**（最容易被跳过、也最重要）：用登录态在控制台外调
   `redeem_paid_order` 传一个乱造的 sig → 必须报验签失败，且
   `SELECT count(*) FROM orders WHERE channel='wechat_h5'` 仍为 0。
3. **金额篡改**：把凭证里的 `amount_cents` 改成 690 再调 → 必须报「金额与套餐不符」。
4. **换账号**：用 B 账号拿 A 的凭证核销 → 必须报「该支付凭证不属于当前账号」。
5. **重复核销**：同一凭证连调两次 → 第二次返回 `already=true`，`orders` 只多一行。
6. **小额真单**：用早鸟月付（¥6.9）跑一遍完整链路，确认
   - 回跳后页面提示「支付成功」且会员状态变为已开通
   - 会员中心「订阅记录」出现 `wechat_h5` 渠道的订单
   - 到期日 = 付款日 + 1 个月

## 六、出问题时的兜底（运营）

用户说「我付了钱但没开通」时，按顺序查：

```sql
-- 1) 这笔订单在不在核销表里
SELECT * FROM public.paid_order_claims WHERE order_id = '<订单号>';
-- 2) 在不在订单表里
SELECT * FROM public.orders WHERE order_id = '<订单号>';
-- 3) 订单归属谁
--    核销表 owner_id 与用户账号不一致 ⇒ 用户下单时用的不是当前账号
```

三种常见原因与处置：

| 现象 | 原因 | 处置 |
|---|---|---|
| claims 无行、orders 无行 | 凭证没到服务端（网关没配 HMAC / 前端没刷到） | 让用户重新打开页面回跳；仍不行则人工补：核对支付平台流水后手工 `INSERT claims + orders`（**必须核对流水**） |
| claims 有行、orders 有行，但用户看不到会员 | 用户当前登录账号 ≠ `owner_id` | 让用户用下单那个账号登录 |
| 报「凭证已过期」 | 超过 7 天 | 核对流水后人工补 |

人工补单务必同时写 `paid_order_claims`（否则同一订单会被再补一次）。

## 七、还没做的（明确列出，不藏）

  （权益回放会据此失效）。
